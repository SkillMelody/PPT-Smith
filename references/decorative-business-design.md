# 装饰商务设计：内容、构图与整册精修

用于用户要求装饰型商务汇报、视觉饱满、内容密集而表达多样的任务。它补充
[动态设计流程](declarative-design.md)，不增加路线，也不替代字体、内容及可编辑性验收。
保留原生母版仍走 template；参考风格后原创走 create；完整设计忠实重建走 recreate。

阅读导航：[任务定义](#1-先定义设计任务避免反复走偏) · [原创边界](#2-参考机制与原创边界) ·
[语义构图](#3-从内容关系到页面构图) · [视觉层次](#4-做出饱满感而不牺牲阅读) ·
[统一与变化](#5-统一语言保留构图差异) · [代表页](#6-先验证代表页再扩展整册) ·
[并行合并](#7-并行作者的交付与合并) · [成稿审核](#8-以最终-ppt-的实际效果验收)。

## 1. 先定义设计任务，避免反复走偏

在 `design.brief` 写清：受众与用途、原始素材、内容口径、原创要求、设计母题、
字体与颜色角色、原生编辑范围，以及参考中采用和舍弃的机制。使用
`design.review_profile = "decorative_business"` 启用本指南对应的构图记录与整册复审。
新任务可在已有 `init` 命令中增加 `--review-profile decorative_business`。
结构请查 `python3 -m engine design schema --section task`；审核结构查 `--section review`。

“装饰”应参与分组、顺序、对照、递进和强调。先回答这页要说明什么关系，再决定
折页、带状、弧线或切角是否有用。不要先选一个图标，再在周围塞入文案。

| 常见迭代误区 | 具体纠偏动作 |
| --- | --- |
| 改颜色，但布局与原稿逐页对应 | 重新拆分信息关系，改变阅读路径、视觉主次与构图拓扑 |
| 信息变多，所有页面变成类表格 | 保留必要数据表；为过程、因果、对照、成果分别设计表达 |
| 为去掉卡片而只剩大图与零散小字 | 恢复浅底、题签、编号轨道、连接带等承载信息的中间层 |
| 图形从齿轮换为山峰，仍是中心图加四角注释 | 改变信息附着位置与阅读路径，让主体图形承担正文关系 |
| 各页精修后全部变成切角矩形 | 检查整册拓扑；统一母题不等于统一容器 |
| 增加阴影、字数或颜色来追求饱满 | 先补充必要证据与结构层次，再检查比例、连接与细节 |
| 构图变多，整册反而散乱 | 保留正文的不同信息关系，收整标题域、基线、字级与图形重量 |
| 逐页看似完整，但无章节过渡或真正结束 | 在锁定页数前安排导航、章节与收尾；按实际功能核对页序 |

## 2. 参考机制与原创边界

参考时记录“为什么有效”，而不是复制“放在哪里”：例如完成度先出现、序号与目标
逐项对应、问题与改进跨中轴相接、图像为成果提供展示空间。不要把参考中的示例数字
当成新任务事实，也不要把概念图片当作真实项目证据。

独立原创需重新建立母题、构图、图文关系和组件组合。代码重写、换色、替换文字，
不能单独证明视觉原创；逐页保留源稿特殊形状、位置与阅读路径应称参考改编或复刻。
通用几何与时间线可以继续使用。对照来源记录相似之处、转化机制和独立设计决定，
据此准确描述工作，不作未经支持的原创性保证。

## 3. 从内容关系到页面构图

先锁定每页内容 ID、单位、分母、阶段、数据来源与未知项，再填写
[逐页计划](../templates/decorative-page-plan.md)。内容较少时可用适当图像与较大的
主信息形成节奏；不能为了铺满页面编造业绩、结论或细节。

| 内容任务 | 阅读顺序与适合的表达 | 必须落在图形上的信息 |
| --- | --- | --- |
| 目标达成 | 结论或完成率 → 目标与实际 → 差距；目标清单与编号轨道、相接折翼 | 每项目标、实际值、状态逐项对应，避免序号只是装饰 |
| 年度进展 | 总完成度 → 各阶段 → 未完成项；大结论与阶段时间线 | 时间节点、阶段交付与剩余任务；完成率注明口径 |
| 详细进度 | 工作流 → 时间区间 → 里程碑；泳道、甘特或连续进度带 | 起止、并行、依赖与验收点，不能仅放四个季度标签 |
| 问题与改进 | 事实 → 原因或待核验假设 → 对应措施 → 验收 | 问题与措施相接；分支、侧三角或折带表达配对与因果 |
| 重要成果 | 核心变化 → 成果图像/数据 → 方法与证明 | 图像有用途说明；大成果区与较细证据区形成主次 |
| 协作与机制 | 角色输入 → 交接 → 共同产出；交织、汇流或闭环 | 责任、输入输出、交接标准，不能只用齿轮代表团队 |
| 计划与风险 | 目标 → 路径或触发条件 → 行动 → 检查 | 阶段门、负责人或应对条件；弧形、扇面不能替代实际逻辑 |

表格与原生图表仍是精确比较的首选之一。给它们安排清晰的结论区和必要标签，
无需强行改成异形。几何隐喻表达关系，图表表达数值；二者不能互相冒充。

### 先安排整册的叙事角色

先按实际汇报内容列出开场、摘要、导航、章节、正文、总结、决策、结束及备查资料，
再决定哪些需要独立成页。完整、多章节商务汇报应考虑目录、每章首页和真正结束页；
短简报、连续读物或用户指定结构可以省略，说明理由即可，不机械补齐固定套数。

经营总结回答“形成什么判断”，决策页回答“需要决定什么”，结束页承担感谢、交流或
明确的下一步。将总结标为 `closing` 不会自动完成收尾。汇报类常用“总结 → 待决策 →
结束”，但仍按场景安排；备查资料可在正文收束前，或放在清楚标明的结束后附录。
若用户要求最后一页必须为感谢页，就把备查资料放在前面。核对实际播放和PDF顺序，
不要仅凭文件名、页角色字段或原材料的顺序判断正确。增删页后更新目录、页码、
章节导航和跨页引用，保留源内容ID与最终页序的映射。

### 逐页构图契约

每个 `design.pages[]` 使用 `composition` 记录作者意图：

- `page_role`：`cover`、`contents`、`section`、`body`、`closing`。正文使用 `body`。
- `claim_content_id`：正文必填，引用本页承载主结论或核心信息的内容。导航页不虚构结论。
- `content_relation`：本页要说明的关系，如目标与实际、阶段递进、问题与改进。
- `layout_family`：真实构图家族，按空间关系命名；不要以颜色或装饰图标命名。
- `reading_path`：按观众实际应读的顺序列出本页已有内容 ID；用位置、尺度与连接支持它。
- `information_attachment`：`inside_structure`、`along_path`、`paired_with_visual` 或 `mixed`。
  选择信息在结构内部、沿路径、与视觉配对或混合的方式；描述必须与渲染一致。
- `layer_plan`：分别写明 `primary`、`secondary`、`detail` 承载什么信息，而非只写“大中小”。
  封面或章节页可以明确说明省略某层及留白的用途，无需为填字段增加信息。
- `rationale`：说明这个构图如何服务内容，以及它和相邻页面为何相同或不同。

这些字段不生成版式，不证明图片美观，也不保证内容已经附着在图形中。编译器只执行
受支持的 scene 对象；作者仍要完成几何、内容绑定和视觉检查。不要为了通过记录检查
给相同构图起不同名字。当前可用字段与约束以 schema 为准。

## 4. 做出饱满感，而不牺牲阅读

先为画面建立三个相互连接的尺度：主层承担结论与结构；中层用浅底、题签、轨道、
分组带或图片裁切组织证据；细层放序号、单位、时间、来源与短说明。中层缺失时，
通常表现为“一个巨大图形加几段悬空小字”。先修复承载关系，再考虑扩大主体。

逐页执行：

1. 划出主结论的空间，确保第一眼能读到；标题、数字与主图不要争夺同一个等级。
2. 将证据放回对应分支、步骤或目标附近。看似对齐但归属错误的说明仍需移动。
3. 用共同底层、连接处、跨区题签或适度叠压连接信息区，避免多个孤立小岛。
4. 检查主、中、细层的占比和空隙。大面积空白先判断是否有节奏作用，而不是自动补卡片。
5. 压缩重复文案、拆出细节页或调整结构后再考虑字号；不靠缩小所有正文解决拥挤。

矩形没有禁令。问题是所有信息不分主次地装进同尺寸卡片；必要的矩形底板、图表区、
数据表和说明带能形成层次。也不要把“饱满”量化为必须填满多少面积或必须放多少对象。

## 5. 统一语言，保留构图差异

统一的是字级、基线、内边距、折痕逻辑、端点、切角比例与颜色角色；可以变化的是
重心、主体方向、分支数量、信息附着位置、图文比例和阅读路径。

把这两类约束在开工时分开写明：

| 全册稳定项 | 按内容变化项 |
| --- | --- |
| 正文标题域、章节导航位置、外边距、注释带 | 主体结构、证据分组与阅读方向 |
| 标题/主数字/正文/注释的字级关系 | 哪项结论或结果成为主焦点 |
| 同类金额、增速、标签的基线与内边距 | 对照、递进、汇流、分叉、面积等表达关系 |
| 线宽等级、连接端点、箭头比例、图形厚度 | 有意义的图文比例、疏密与明暗节奏 |

不要用逐页移动标题、同时改变所有字号和数字基线来制造多样性。共享标题域不等于
正文共享布局；封面、章节和资料索引可以有明确的角色例外。数值坐标与字号按当前
画布、语言和内容制定，不能把案例中的坐标直接当成通用标准。

优先修复失去秩序的少数页：把失衡的大数与辅助说明重新分级；缩短无信息的长连接；
降低过重的中心、环路和尖角；对齐同类数字而保留原有分叉或递进关系。不要把有效的
时间线、比例拼图等一起改回同一种容器。只为解决已观察到的问题调整图形重量，
并不要求所有商务报告都用细线。

- **颜色**：先定主色与强调色的职责，再区分次要信息。不要每个模块机械分配一种饱和色；
  同一语义沿全册保持一致，关键变化才获得更强的颜色。
- **字体**：区分结论、数字、短题签、正文、注释。中文与数字混排检查基线与间距；
  不把每页都写成同长度标题加三段相同字号正文。
- **图形**：折面厚度、遮挡关系、接缝、端帽和线宽有一致逻辑。连接线应真正接到对应结构，
  重叠应表达前后关系；阴影只用于需要区分的层次。
- **图片**：成果图像、概念插画、装饰图像分别说明用途。封面有材质感时，正文通过折面、
  层叠与比例延续语言，不必把每一页都做成写实场景。
- **非矩形文字**：按可见形状的内部安全区放字，不按外接矩形。环带按厚度中线排布，
  弧边留足距离，尖角与切角避开文本；逐字检查浅字是否落入浅色孔洞或遮挡区域。

## 6. 先验证代表页，再扩展整册

从实际内容中选择目标达成、总进展与详细时间线、问题改进、成果图文、风险或计划等
代表页。没有某类内容便不补造页面。先跑实际 Office 字体预检，再制作代表页；看清晰
单页与小型总览，确认信息密度、主次与构图差异后扩展。常规内部修订无需再次请求批准。

将所有页面列成“页角色—结论—内容关系—构图家族—信息附着—明暗/图文比例”的矩阵。
比较相邻页面、同章连续页面和全册：是否每页都是左文右图？是否只是中心图标不同？
是否所有细节都退到页底？是否每张重要成果都获得了足够展示空间？

连续比较、阶段拆解或系列页可以复用骨架，此时保持可比位置，并把变化用于真正不同
的内容组件。不要为追求形式多样打乱可比关系，也不要设置固定“每类只能出现几次”
或“必须有几种图形”的审美配额。重复是否合理由内容目的与整册视觉证据决定。
用户明确要求逐页主体结构不同，则按该要求设计，不能以“同一章节”或“系列页”为由
自行豁免。除相邻页外，还要比较相隔较远的同类页面；不同名字、不同图标或外轮廓
可能仍是同一“左图右文”或“中心加四角”骨架。

运行 `python3 -m engine design composition-check --task-dir "$TASK"` 获取构图记录的
诊断提示。它帮助定位需要查看的页面，不给出审美通过结论；相同家族可能有合理用途，
不同家族名称也可能掩盖同一种实际布局，都必须看真实预览后判断。
当前提示规则是同一声明结构连续出现至少 3 页，或至少 5 个正文页中某结构占比达到
60%；结构按家族与信息附着方式分组，导航页中断连续计数。这些只是定位线索，
不构成交付门槛，也不能识别作者给相同版式换名的情况。

同一命令还输出 `body_claim_observations`（正文主结论原生文字框的绝对位置、字体与
对齐）、`body_claim_anchor_patterns`（相同基础锚点的分组）及 `navigation_inventory`
（实际页序中的已声明角色、目录、章节和结束页）。用它们定位标题漂移或角色遗漏的
疑点，不要求只有一种锚点或必须出现所有导航角色。文字框坐标不是渲染后的字形基线；
主结论也不一定就是页标题，角色声明更不能证明该页真正完成了总结或结束。仍需读图。

## 7. 并行作者的交付与合并

分工前共享已核对内容、统一设计语言、代表页、整册矩阵和每页 `composition`；分配
互不重叠的页面与文件。不要只给各作者一句“装饰、折页、饱满”，否则容易全部收敛为
同一组切角容器。正文数据、标签与颜色使用命名字段，避免靠位置数组传递语义。
同时交付稳定项与变化项：共享标题/导航、字级、内容边界、线宽等级和底注区；为各页
保留不同的信息关系。不能一边要求每页不同，一边只提供一个必须复用的完整正文框架。

每位作者交付修改页、对应内容 ID、真实候选预览、未解决问题，以及来源版本或构建 ID。
合并者确认这些预览对应实际合入的 scene，而不是作者早先的私有版本。发生颜色异常、
编号错位、十六进制值露出等现象时，先查数据字段与绑定，再调整视觉。

合并后必须重新渲染并做整册检查。单页各自合格不代表合并后的节奏合格；若全部回到
方框、折带或中心四角结构，保留内容和设计语言，重新设计部分页面的拓扑与附着方式。

## 8. 以最终 PPT 的实际效果验收

使用正式工作流从候选 PPTX 生成实际预览。源 scene 预览、拼图和导出成功日志均不能
代替成稿检查；如两种渲染的图表排序、折线或文字不同，以实际交付文件为复核对象。

逐页检查：结论可见；数据与单位正确；说明跟随正确对象；字号和中文完整；边界、
折角、圆环与遮挡处文字可读；连接与层叠合理；图表图例与系列对应；概念图未被当成
证据。结构检查未报错，仍可能存在白字落入白洞、说明归属错误等视觉问题。

独立审阅者在原有逐页审核之外填写 `deck_composition`：`status`、`observations`、
`reviewed_page_ids`。初始状态为 `revise`；记录实际查看过的页面与具体观察，例如
哪组页面重复、哪些系列页的重复有必要、主中细层是否完整，以及仍需修改的页面。
逐页通过或继承既有逐页证据，不能自动批准新候选的整册构图。

在 `observations` 中分别写出三方面证据，无需新增JSON字段：

| 检查维度 | 实际查看什么 |
| --- | --- |
| 构图多样性 | 正文的信息拓扑、附着和阅读路径；重复的具体页及其理由 |
| 全册规整度 | 标题/导航位置、金额和增速基线、边界、线宽等级、密度与重心 |
| 叙事完整性 | 目录与实际页序、章节起点、总结/决策/结束的功能、附录位置 |

对比版本时同时看总览和问题页，记录“改善了什么、退化了什么、保留什么”，不要把
某一维度的改善等同于整册质量提高。总览用于发现疑点；裁切、轴标签碰撞或形状内
文字安全区需回到该构建的实际单页或原像素局部确认。误报可以撤回并保留理由，
不能为了响应缩略图误读去修改正确页面。

`observed_node_ids` 必须覆盖实际核对过的所有带 `content_id` 的对象，包括页码、
来源、脚注、图表与表格，不能只列代表性对象。用候选 `objects.json` 的 bindings
与 scene 对照核对；不要自动把“需要检查”的ID预填成“已检查”。协作审核保留各自
